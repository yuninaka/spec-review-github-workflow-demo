# spec-review-github-workflow-demo

「[個人実証(番外編)：型分離PoCを作ろうとして、作らなくてよいと気づくまで](https://zenn.dev/yuninaka/articles/type-separation-spec-review-retrospective)」で提案した、仕様書レビューをGitHubの標準機能(プルリクエスト・ブランチ保護・Actions)で組み立てる運用案を、実際に動かして検証するためのデモリポジトリ。

## このリポジトリで検証していること

記事内の「GitHubを使う場合の運用案」で挙げた対応関係を、実際の設定・操作で確認している。
**単一アカウントでの検証のため、実際に確認できた範囲とできなかった範囲がある**(詳細は下の「検証ログ」を参照)。

| 記事内の設計 | GitHubの実際の機能 | このリポジトリでの検証 |
|---|---|---|
| `DraftSpecification` / `ApprovedSpecification`の型による区別 | プルリクエスト上の変更 / 保護されたブランチ(`main`)にマージされた状態 | ✅ 検証済み。ブランチ保護ルールにより`main`への直接pushが実際に拒否されることを確認した(PR #1参照) |
| 残った独自ロジック①(構造化データのルールベースチェック) | プルリクエストに対して自動実行されるチェック | ✅ 検証済み。`.github/workflows/spec-check.yml`が実際にPR上で実行され、必須セクションの有無を確認した結果がコメントとして投稿されることを確認した(PR #1参照)。これは記事の第3段階で検討した「構造化データの矛盾チェック」の簡易な代替であり、AIは呼び出していない |
| 残った独自ロジック②(固定プロンプトによるAI確認) | CIはAIを呼ばず、PR時にレビュワーへ固定プロンプトの実行を促す | ✅ 検証済み(促す仕組みのみ)。`.github/workflows/spec-review-prompt.yml`が、PRの作成・更新のたびに`.github/SPEC_REVIEW_PROMPT.md`(案件非依存の固定プロンプト)へ仕様書本文を埋め込んだ内容をPRコメントとして投稿することを確認した(PR #1参照)。**実際にこのプロンプトをAIへ投げて結果を確認する作業自体は、レビュワーが外部のAIツールで行う想定であり、この仕組みではAIを一切呼び出していない**。プロンプトが案件をまたいで転用できるかどうかは、「確認してほしい観点」を書き換えるだけで済む設計にはしたが、実際に複数の異なる仕様書で試してはいない |
| 承認なしではマージできないこと | プルリクエストのレビュー必須設定 | ✅ 検証済み。未承認のPRに対して`gh pr merge`を実行したところ、ブランチ保護により拒否されることを確認した |
| 承認記録の永続化 | プルリクエストのレビュー承認 | ⚠️ 設定は確認したが、承認そのものは未検証。GitHubの仕様上、PR作成者は自分自身のPRを承認できず、この検証には別アカウントでのレビューが必要(下記参照) |
| 「承認後に仕様書が更新されたら再レビューが必要」 | ブランチ保護ルールの「新しいコミットがpushされたら既存の承認を無効化する」設定(`dismiss_stale_reviews`) | ⚠️ 設定(`dismiss_stale_reviews: true`)がブランチ保護に反映されていることはAPIで確認したが、承認→追加push→無効化という一連の動作は、上記と同じ理由で未検証 |
| 差分の可視化 | プルリクエストの差分表示 | ✅ 検証済み。PR #1のFiles changedタブで、変更行が実際に色分け表示されることを確認した |

## 構成

- `spec/current-spec.md`: 「承認済み仕様書」に相当するダミーファイル。内容は検証用の架空のものであり、実在のプロジェクト・企業とは一切関係ない
- `.github/workflows/spec-check.yml`: プルリクエストに対して自動実行されるルールベースのチェック。仕様書に必須セクション(対象範囲・変更内容・確認事項)が揃っているかを確認し、結果をコメントする(AIは呼び出さない)
- `.github/SPEC_REVIEW_PROMPT.md`: 案件非依存の固定プロンプト。「確認してほしい観点」だけを案件ごとに書き換えれば転用できる設計にしている
- `.github/workflows/spec-review-prompt.yml`: プルリクエストの作成・更新のたびに、上記の固定プロンプトへ仕様書本文を埋め込んでPRコメントとして提示する。CIはこの時点でAIを呼び出さない。実際にAIへ投げて結果を確認する作業はレビュワーが外部ツールで行う想定

## 検証ログ

1. `main`にブランチ保護ルール(承認1件必須・`dismiss_stale_reviews`有効・管理者にも強制適用)を設定した
2. `main`への直接pushを試みたところ、`GH006: Protected branch update failed`で実際に拒否された
3. ブランチを切ってプルリクエスト(#1)を作成したところ、`spec-check`ワークフローが自動実行され、必須セクションが揃っている旨のコメントが実際に投稿された
4. 承認なしで`gh pr merge`を実行したところ、「the base branch policy prohibits the merge」で実際に拒否された
5. PR #1を自分自身で承認しようとしたところ、GitHubの仕様により`Can not approve your own pull request`というエラーになった。実際の組織運用ではレビュワーが別人であるため問題にならないが、**単一アカウントでのこのデモでは、承認そのものと、承認後の再push→無効化の一連の動作までは検証できなかった**
6. そのため、PR #1は「未承認でマージがブロックされている状態」のまま残している。これも記事の主張(承認なしでは後工程に進めない設計が機能すること)の証拠として有効だと判断した
7. `spec-review-prompt.yml`を追加し、PR #1のブランチに仕様書の変更を追加pushしたところ、更新後の仕様書本文を埋め込んだ固定プロンプトが実際にPRコメントとして投稿されることを確認した。CIはこの時点でAIを一切呼び出していない(ワークフローの中身はテンプレートファイルの読み込みとコメント投稿のみ)

## 注意

これは概念実証のためのデモであり、実運用を想定したものではない。ルールベースのチェック(`spec-check.yml`)は必須セクションの有無を確認するだけの最小限の実装にとどめている。固定プロンプトによるAI確認(`spec-review-prompt.yml`)は、CIがプロンプトを提示するところまでは自動化・検証済みだが、実際にAIへ投げて確認する作業自体、およびそれが複数の異なる案件で本当に転用できるかは、このデモの範囲では検証していない。
